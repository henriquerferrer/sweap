# Running sweap 24/7 on one Max subscription: what burned the week, and the design (2026-09-22)

Trigger: the consumer A F13 run (Sep 18–20, 50 PRs merged) took a Max 20x account to
93% of its weekly limit in 2.5 days. Henrique's goal is to run sweap on consumer A
continuously. This memo records what was measured, what was researched, the
design that follows, and every claim the design rests on — numbered so a
refuter can kill one without the others. Refuted claims are struck in the
"Refutation" section at the end, before anything was built.

## Measured (from the consumer A session transcripts, priced at API list rates)

| line | Sep 18–20 | share |
|---|---|---|
| cache writes (5-min TTL, Opus 5 subagents) | $1,055 | 56% |
| cache reads (1.56B tokens) | $763 | 41% |
| output (2.2M tokens) | $62 | 3% |
| Fable 5.1 (orchestrator only) | $71 of the total | 4% |

- 10,390 requests, median context 132k, 3,023 requests over 200k, max 806k.
- Of 399 cache rewrites larger than 50k tokens, 379 followed a gap of more than
  5 minutes. Bucketed by the gap before the request (Opus subagents only):

| gap | requests | cache written |
|---|---|---|
| ≤5 min | 9,131 | 23.5M |
| 5–15 min | 330 | 121.1M |
| 15–60 min | 36 | 8.0M |
| >60 min | 2 | 0.9M |

- The eight "lane runner" agents (Henrique's brief in consumer-a-run-notes, not a
  sweap mechanism) grew from 37k to 758k and 806k context and read 464M tokens;
  their job between items was waiting on `sweap-merge watch`.

## Researched (dated sources in the session; the load-bearing ones)

- Anthropic: the 5x/20x multipliers are per 5-hour window; the weekly limit is a
  separate unpublished number. Measured weekly ratios are 1.7x (Anthropic's own
  2025 hour table) to 2.1x (botfarm.run, Mar 2026: ~$523 vs ~$1,100 API-value).
  claudecodecamp (63 reset cycles, Apr 2026): Max 20x 7-day window median $1,378.
- Three independent measurements (claudecodecamp; note.com/ai_hack_dx, 61,724
  events; GitHub #77001) say cache reads barely move the weekly meter while cache
  writes and output dominate. No official formula exists. Our run's writes plus
  output ($1,120) match the measured week size at 93%; its list price including
  reads ($1,880) does not.
- Claude Code docs (prompt-caching, fetched 2026-09-22): every request outside
  the main conversation — subagents, workflow agents, forks, compaction — gets a
  5-minute cache TTL by default, even on a subscription. `subagentPromptCacheTtl`
  / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` set it to `1h` (v2.1.242+). The API
  bills 1h writes at 2x input, 5m writes at 1.25x.
- Verified by experiment (2026-09-22, Claude Code 2.1.280, Max subscription):
  `claude -p --settings '{"env":{"CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL":"1h"}}'`
  produced subagent cache writes reported as `ephemeral_1h_input_tokens`
  (10,347 and 1,854), zero `ephemeral_5m`. The `--settings` env route is the
  same mechanism the scaffold already uses for `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP`.
- Workflows doc: a workflow run pauses when an agent hits a usage limit and
  resumes after the reset (v2.1.271+, interactive subscription session,
  `autoContinueAtUsageLimit` on, reset within 24h, at most two waits per run;
  a third hit fails the agent, which resolves to `null`). A relaunch replays
  completed agents from cache. `pipeline()` runs items concurrently; a serial
  loop is a plain `for` with `await`. Scripts cannot read files or sleep.
- Status line doc: the JSON a status-line command receives carries
  `rate_limits.five_hour` and `rate_limits.seven_day` (`used_percentage`,
  `resets_at`) for Pro/Max, after the first API response; `refreshInterval`
  re-runs the command on a timer while the session is idle.
- Sub-agents doc: subagents may spawn subagents to a depth of three below the
  main conversation; `experimental.cacheTtl` frontmatter is read only from
  subagent files (so it cannot reach a `general-purpose` implementer).
- Headless doc: `claude -p` without `--bare` loads plugins, hooks and CLAUDE.md
  and uses the subscription; it never waits at a usage limit.

## Design

D1. The scaffold seeds `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h` into the
    consumer's `.claude/settings.json` `env` block, exactly as it seeds the
    pressure-reap key today (add-if-absent, never overwrite a value).
D2. A `sweap:run` plugin workflow (`plugin/workflows/run.js`) drives the per-item
    loop: a Scope agent lists the runnable frontier in drain order (or takes
    `args.ids`); then, strictly one item at a time, a fresh implementer agent
    plans, implements with TDD, dispatches the reviewer(s), pushes, opens the PR
    and exits returning the PR number; a fresh small merge agent runs
    `sweap-merge watch <n>` until a terminal word, verifies the flip and the
    cleanup, and returns the word; on `failed`/`behind` a fresh fix agent gets
    the failure summary and the loop re-arms (bounded rounds); `attended`,
    `undecidable`, `held-by`, `blocked` and a `null` (limit or API death) stop
    the run with a report. The run session records `.claude/sweap-run.md` as
    today.
D3. A usage tap: a plugin `bin/` script for the `statusLine` command that
    appends `{ts, five_hour, seven_day, session}` lines to a log on every
    refresh, plus a report tool that joins the log with the transcripts' token
    counts and fits the weekly meter's weights per token kind. This is the
    instrument that settles C5 for this account.
D4. The playbook's Run core names `/sweap:run` as the way a run drives items;
    the hand-written lane-runner brief is retired. Every heading is kept.

## Claims (each falsifiable; a refuter scores each one)

C1. The 5-minute subagent cache TTL expiring during waits on CI is the dominant
    cost of the last run: 83% of subagent cache-write tokens followed a gap
    longer than 5 minutes, and cache writes were 56% of list price.
C2. Setting the subagent TTL to 1h cuts that line by roughly 75% (from ~$978 to
    ~$243 on the measured shape), because the 2x write surcharge applies to
    ~2,500 incremental tokens per turn while the expiries it removes are whole
    contexts of 300k–800k.
C3. The settings `env` route delivers the 1h TTL to `general-purpose`
    subagents on a subscription (experiment above), and the scaffold can seed it
    without touching an existing value.
C4. Moving the loop into a workflow with a fresh agent per item removes the
    lane-runner contexts (464M reads, 122M writes) without a quality loss: the
    implementer was already a fresh agent per item, the runner only drove and
    waited, and cross-item lessons already travel by file (lane-lessons.md).
C5. The weekly meter weights cache reads at or near zero and cache writes and
    output near API price; therefore a post-change 24/7 serial run (~$120
    meter-dollars/day) fits inside one Max 20x week (~$1,100–1,400).
C6. A workflow inside an interactive subscription session is the better host
    for a 24/7 loop than an external `claude -p` driver: it pauses and resumes at
    5-hour limits on its own, replays completed items on relaunch, keeps hooks
    and the permission classifier, and ships in the plugin.
C7. The merge wait belongs in a small separate agent, not the implementer: a
    ~40k-context watcher's rewrites are cheap even when its cache expires, and
    with the 1h TTL they are nearly free.
C8. The status-line tap is a sanctioned, sufficient instrument to measure the
    meter's per-token-kind weights: it samples `seven_day.used_percentage` on a
    timer while the run is going, and the transcripts give the token kinds per
    interval.
C9. Nothing in this design needs a second subscription; the decision to buy one
    waits for C5's measurement.
C10. The two-waits-per-run cap on the workflow's limit pause is not a
    practical blocker for a serial loop: at ~$25 per 5-hour window against a
    measured ~$164 window, the loop should not hit the 5-hour limit at all, and
    a weekly wall is a relaunch, not a loss.

## Refutation

Three refuters, distinct lenses (harness mechanics; economics and measurement;
run design and quality), each scoring every claim 0 (stands) to 1 (refuted),
with citations. A claim with two or more scores at or above 0.5 is struck.

| claim | mechanics | economics | run design | verdict |
|---|---|---|---|---|
| C1 5-min expiry during waits dominates | 0.15 | 0.25 | 0.25 | stands, corrected |
| C2 1h TTL cuts writes ~75% | 0.20 | 0.85 | 0.20 | stands by count; the figure is dead (below) |
| C3 settings env route delivers 1h | 0.15 | 0.10 | 0.15 | stands, re-verified |
| C4 per-item agents lose nothing | 0.35 | 0.20 | 0.85 | stands by count; "nothing" is false (below) |
| C5 reads count ~0, 24/7 fits | 0.60 | 0.80 | 0.20 | **struck** |
| C6 workflow beats a -p driver | 0.30 | 0.10 | 0.60 | stands, corrected |
| C7 separate small watcher | 0.15 | 0.30 | 0.35 | stands, justified differently |
| C8 status-line regression finds the weights | 0.55 | 0.50 | 0.30 | **struck** |
| C9 no second subscription needed yet | 0.30 | 0.30 | 0.10 | stands, contingent on the measurement |
| C10 the 5-hour cap is not hit | 0.30 | 0.30 | 0.55 | stands; the $25 figure is dead |

**Corrections that survived, in the order they change the numbers.**

- The tally undercounted output 3.8x: Claude Code writes one transcript line
  per content block with a RUNNING `output_tokens`, and the scripts kept the
  first line per message id. Corrected Sep 17–20: writes $1,055 (52%), reads
  $763 (37%), output $230 (11%), total $2,047. Writes still dominate.
- 89% of the expiry tokens (116M of 130M) belong to the eight lane runners.
  Their gaps were their own 600-second foreground Bash calls — `bash
  /private/tmp/.../<poll script>`, `for i in …`, `until ! gh …`, `deadline=$((
  …` — hand-rolled CI polling around and instead of the driver, whose default
  `--budget` is 100 s. Implementers contributed 6.3M (their own long test
  runs); reviewers 0.1M.
- C2's "$978 → $243" counted the lane runners' expiries, which D2 deletes
  outright. On the post-D2 shape a global 1h TTL saves ≈$39 on implementers,
  costs ≈$35 in 2x writes on them, and makes reviewers 58% dearer ($46 → $72),
  because they never idle: net ≈ $0 ± $40 per run. Break-even for a 1h TTL is
  expiry tokens avoided > 0.6 × incremental tokens written; only an agent that
  idles past five minutes on purpose clears it. So D1 is DROPPED as a global
  setting. The one agent that idles by design, the merge watcher, carries
  `experimental: cacheTtl: 1h` in its own file, which is the per-agent form the
  docs provide (ignored while on usage credits; fine).
- C3 was re-verified on the design path, not the CLI flag: a project
  `.claude/settings.json` `env` block, `claude -p`, an Opus subagent — cache
  writes reported as `ephemeral_1h_input_tokens` (17,423 and 1,854), zero 5m.
  Recorded for the day a per-project TTL is wanted; nothing ships it.
- C5 is struck. The "reads ≈ 0" inference matched one number to a range, and
  the number was wrong (output undercounted) and consumer-only (the meter is
  account-wide: the other projects added $201–409 of writes+output in the same
  week). Account-wide writes+output over the seven days before any plausible
  reading time is $1,448–1,729, which at 93% implies a week of $1,557–1,859 at
  read weight 0 — outside the range the memo's sources report. Read weights of
  0, 0.1 and 0.25 all fit; only ≥0.5 fails. The official costs doc says cached
  re-reads "still draw usage for the whole conversation". Nobody recorded when
  the 93% was read. The 24/7 fit is therefore UNMEASURED, and the corrected
  post-D2 estimate at the F13 run's own throughput (72 of 72 hours active, ~17
  PRs/day, median four concurrent subagents) is $142/day at read weight 0,
  $185 at 0.25, $316 at list — $994–1,295/week for consumer A alone, before the
  $200–400/week the account spends elsewhere. That is AT the measured week.
  A strictly serial loop does fewer PRs per day and costs proportionally less;
  what the single subscription buys is a throughput, not a yes.
- C8 is struck: on a serial run reads, writes and output move together and a
  regression on status-line samples cannot separate them (simulated on the
  run's hourly mix: writes ±0.10, reads ±0.25, output ±0.80). The status line
  also may not refresh its `rate_limits` while the main session idles behind a
  workflow, and the user's status line is already a command a plugin cannot
  replace. What survives of D3 is the RECORDER: a tap that logs every reading
  with its timestamp, wrapping the existing status line, so the next 93% has a
  time. The weights come from three isolated bursts in an otherwise idle
  account, each sized to move the meter ≥2%: reads only (a ~500k-context agent
  answering ~60 one-token questions inside the TTL, ~30–100M reads), writes
  only (force ~8 expiries of a 500k prefix, ~4M writes), output only (one
  ~1M-token generation). Read `seven_day.used_percentage` before and five
  minutes after each. Three differences, three weights, no regression.
- C4: "without a quality loss" is false on the record. The lane runners also
  ran premise verification one item ahead (lane-verified-premises.md, 292
  lines), built one mid-lane fix that was no item (consumer A #371), re-derived
  line numbers after a sibling merged (DV.47 after DV.46), and knew that an
  `attended` word meant "queued". None of that lived in a file the plugin
  could name. Response: the eight transferable lessons are folded into the
  worker brief and the agents (premise counting; unit tests by name;
  universals scan; sequential reviewers, two rounds; push in its own call;
  discovered-inbox grep; the security skill's empty-diff trap; a merged
  sibling's claims rot), the workflow threads each item's premise report into
  the next item's prompt, a Resume stage runs first (consumer A today has an FP.2
  worktree with 13 uncommitted files and no PR), and the frontier is
  recomputed before every item. The one-ahead Explore pass is not rebuilt: it
  bought latency, not correctness, and the implementer's own premise step
  covers it.
- C6/C10: the workflow's usage-limit pause is two waits per RUN LIFETIME, not
  "twice in a row"; a weekly wall (reset > 24 h away) fails the agent at once,
  and a relaunch is a human at the keyboard in the same session or a resumed
  one; it never pauses in a background session; a Mac asleep > 30 min turns
  auto-continue into "press enter". The host must be a foreground interactive
  terminal on a machine that does not sleep — which the two CI runners already
  require. Workflow agents inherit the SESSION model unless the script names
  one; this session's is Fable 5.1, the cost basis is Opus 5, so `run.js`
  passes `model: 'opus'` explicitly. The 5-hour window: the run's maximum
  rolling five-hour spend was $220 list / $156 writes+output with no limit hit,
  so the cap is at least that; a serial loop spends ≤$50 per window under any
  weighting. `autoContinueAtUsageLimit` must never be seeded into a project
  settings file: there it turns the feature OFF.
- Driver defect, confirmed and fixed: `sweap-merge` classified a GitHub run
  with status `pending` or `requested` as `attended` ("needs approval"). Every
  `attended` consumer A ever saw (10 of 145 state files; PRs #236 … #385) was a run
  queued behind a `concurrency:` group or the busy two-runner fleet, and every
  one of those PRs then merged untouched — while `attended` is terminal and
  halted unattended lanes. Now `pending`; `waiting` and `action_required` stay
  `attended`. Two driver tests pin it.

**What was built (sweap 0.31.0).** The `/sweap:run` workflow with its wiring
test; the `merge-watcher` agent (Sonnet, Bash/Read/Grep, 1h cache, foreground
bounded watch, attended and held-by handling, red classification, post-merge
verification); the driver's `pending`/`requested` fix; the security reviewer's
empty-diff instruction; `sweap-frontier`; `sweap-usage-tap`; the playbook's
"Who holds the loop", the agent form of "Merge and wait", eight worker-brief
lines, the mechanisms row; `/milestone` prints the `/sweap:run` batch next to
the goal (superseded in 0.33.0: the goal's own text launches the workflow and
the second paste is gone — docs/research/2026-09-23-one-paste-kickoff.md).

**Not built, on purpose.** A global subagent TTL (net ≈ $0); a second
subscription (the throughput question is unmeasured); a one-ahead Explore
stage; any change to how the weekly meter is inferred.

**Owed by the consumers.** consumer A: the F13 run file says "resume with a fresh
lane runner" — the resume is `/sweap:run {"ids": [FP.2 … FP.25, F12.16 …
F12.24]}` after the plugin update (what happened: the run was launched bare
on 2026-09-23 and started on FP.2 with the whole frontier in scope — see the
2026-09-23 memo); `CLAUDE.md:71` still says the e2e command
runs vitest (it does not; lane lesson 8) and line 60's connection claim is
falsified (lane-verified-premises.md:54); the FP.2 worktree holds 13
uncommitted files the Resume stage will hand to the first implementer; the
`sweap-usage-tap install` snippet goes into the user's settings so the next
reading has a time. First run of the workflow: watch the permission classifier
(script-computed prompts are not user requests in auto mode) and the model the
implementers actually run on; both are cheap to read from the transcripts.
