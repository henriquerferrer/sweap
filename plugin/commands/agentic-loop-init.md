---
description: Scaffold sweap's project-owned files (CLAUDE.md config, ROADMAP index + roadmap/ items dir, justfile, .github) into this repo. Idempotent.
---

This project is normally auto-scaffolded on first session by the sweap plugin's
`SessionStart` hook (`hooks/scaffold.sh`) — you're running this command as the
explicit repair/re-run path (e.g. the hook didn't fire, files got deleted, or
you want to re-check for drift). It shares the exact same scaffold logic as the
hook, so there is only one implementation to keep correct.

Run the scaffold now:

```bash
"${CLAUDE_PLUGIN_ROOT}"/hooks/scaffold.sh <<< "$(printf '{"cwd":"%s","source":"init-command"}' "$PWD")"
```

This mechanically, idempotently:

1. **Never overwrites project-owned files.** For each template file under
   `${CLAUDE_PLUGIN_ROOT}/templates/`, if the destination already exists in
   this project, it's skipped. Only missing files are created (the
   sweap-managed set in item 3 is the sole exception).
2. **CLAUDE.md merge:** if the project already has a `CLAUDE.md` but it lacks a
   `## sweap config` block, appends the template's `<!-- sweap:begin -->` …
   `<!-- sweap:end -->` region (playbook pointer + config block + standing-prefs,
   together, so the playbook pointer can never be dropped by the merge). If a
   `## sweap config` block already exists, leaves it — idempotent.
3. **Audit-gate control (sweap-managed):** installs
   `.github/workflows/audit-gate.yml` plus the VENDORED scripts
   `.github/scripts/audit-gate.sh`, `.github/scripts/roadmap-lint.sh` and
   `.github/scripts/ci-lane.sh`, if the project has a `.github/workflows/`
   directory (the sync re-runs after the template copy, so on a fresh repo the
   scripts land in the same session as the workflow that calls them). Like the gitignore rules below,
   this runs BEFORE the already-scaffolded fast-guard, so a repo that adopted
   sweap before the audit gate existed gains it on its next session rather than
   never — that gap is exactly how a consumer repo ran for days with a malformed
   audit record and no check to catch it.
   Unlike every other scaffolded file these four are **kept current**, not just
   created: if the plugin's copy differs, the project's is rewritten. Each
   carries a `# Code generated by sweap <version> (source sha256:<hash>). DO NOT
   EDIT.` stamp line (after the shebang for scripts, line 1 for the YAML) — the
   stamp is informational; drift is detected by content comparison, never by
   the stamp. The sync is skipped on `/compact` and `/clear` (this command
   passes `source: init-command`, which always syncs). A consumer
   silently running an old gate is the bug this subsystem exists to fix. The
   gate is vendored (not checked out from sweap in CI) so the check needs no PAT
   and no cross-repo access — both repos being private would otherwise require a
   secret whose expiry would block every PR.
4. **Runtime gitignore rules:** ensures the project's `.gitignore` excludes
   sweap's runtime files — `session-main-redcheck.sh`'s marker file
   (`.claude/main-red-*.flag`), a legacy run-journal file
   (`.claude/sweap-board.md`), the run file `/milestone` writes at kickoff
   (`.claude/sweap-run.md`) and the merge driver's state dir
   (`.claude/sweap-merge/`) — appending each line only if missing, creating
   `.gitignore` if absent, never duplicated. The scaffold self-heals these on
   every session start (the gitignore step runs before the already-scaffolded
   fast-guard), so an existing project gains a newly-added rule on its next
   session; this command is the manual repair path.

**How a session reaches the plugin's scripts (no setup needed).** Claude Code
adds `<plugin-root>/bin` to the Bash tool's PATH for every ENABLED plugin, so
while sweap is enabled the project gets four bare commands: `sweap-merge` (the
merge driver), `sweap-roadmap-lint` (the per-item spec gate), `sweap-stranded`
(the stranded-branch detector) and `sweap-note` (the discovered/idea inbox
writer). Nothing is written into the project and nothing is vendored. This is
the *only* way a session can reach them: `${CLAUDE_PLUGIN_ROOT}` is exported
for HOOK execution only and is UNSET in a model-issued Bash tool call, so the
old `bash "${CLAUDE_PLUGIN_ROOT}/hooks/<x>.sh"` spelling expanded to
`bash /hooks/<x>.sh` and silently could not run. The merge driver is
deliberately **not vendored** into `.github/scripts/` the way `audit-gate.sh`
is: it resolves the merge gate (`pre-merge-gate.sh`) and the post-merge hooks
from its own directory, so it must run from the plugin dir beside its siblings
— a vendored copy would find neither. `bin/` gives it a stable, allowlistable
name *without* moving the script out of the plugin dir.

Report back to the human exactly what the script's summary said it created,
kept, or merged. Then walk through this checklist regardless of what the
script reported (these are the fill-ins the script cannot do for you):
   - **Decide how the audit gate is enforced — check the plan first.** Run
     `gh api repos/{owner}/{repo}/rulesets` to see which case you are in.
     - *403 "Upgrade to GitHub Pro"* (a private repo on Free — sweap's default
       assumption): rulesets and branch protection do not exist for you, and
       there is NOTHING to configure. Enforcement is `pre-merge-gate.sh`, which
       already denies any `gh pr merge` whose check rollup is not fully green,
       and `audit-gate` is now in that rollup. Tell the human plainly that a
       merge from the GitHub web UI bypasses the hook and is caught only after
       the fact by `post-merge-auditcheck.sh` — do not claim protection the
       plan cannot provide.
     - *Otherwise* (public, org, or Pro): make `audit-gate` a REQUIRED check
       pinned to the GitHub Actions app (id `15368`), never "any source". Do not
       add a required-review rule on a solo repo — you cannot approve your own
       PR and it wedges every merge.
     Either way keep the default `GITHUB_TOKEN` read-only. Path-protecting
     `.github/scripts/**` needs an org-scoped push ruleset and is not available
     to a personal repo — the scaffold's rewrite-on-drift is what covers those
     files instead.
   - Fill in the `verify.typecheck` / `verify.lint` / `verify.e2e` commands in
     the `## sweap config` block (`verify.e2e` is what CI runs in full — unit +
     integration + e2e — as the authoritative merge gate; locally, agents run only
     the part a change touches).
   - Fill in every `# <fill in for your stack>` stub in `justfile` (recipe
     bodies for `lint`, `typecheck`, `test`, `e2e`, and optionally
     `services-up`/`services-down`). Leave the `merge` / `merge-status`
     recipes alone — they are complete.
   - **Allowlist the merge driver** in the project's `.claude/settings.json`:
     add **`Bash(sweap-merge:*)`** to `permissions.allow` — and, if they should
     also run unprompted, `Bash(sweap-roadmap-lint:*)`,
     `Bash(sweap-stranded:*)` and `Bash(sweap-note:*)`. The `:*` suffix is the
     documented equivalent of a trailing ` *`, so `Bash(sweap-merge:*)` matches
     `sweap-merge watch 12` and bare `sweap-merge`, and the space it implies
     stops it matching some unrelated `sweap-merge…` program. Without the rule
     the driver prompts while `Bash(gh pr merge:*)` does not, so every run
     routes around it — that is exactly how consumer A's first run with the driver
     installed used it zero times. Allowlisting is only possible because the
     name is stable: a prefix pattern against the script's own path is not,
     since the plugin cache path carries a commit sha and changes on every
     version bump.
   - Fill in every `<fill in for your stack>` step in
     `.github/workflows/ci.yml` (toolchain setup, e2e prerequisites, optional
     `services:` blocks, the e2e artifact path).
   - Write `.github/scripts/ci-status.sh` and `.github/scripts/ci-summary.sh`
     to emit the JSON status-block convention documented in CLAUDE.md's CI
     section (or generate them via the `agentic-ci` skill).
   - Generate a `CLAUDE_CODE_OAUTH_TOKEN` repo secret (`claude setup-token`,
     then `gh secret set`) so `.github/workflows/claude-review.yml` runs.
     That workflow is SWEAP-MANAGED as of 0.20.0 — the scaffold keeps it in
     lockstep with the plugin's copy, so a fix to the verdict gate reaches this
     repo on the next session as an ordinary working-tree diff to review and
     commit. Do not hand-edit it; it has three seams instead:
     `RUNNER_LABELS` (repo variable, a JSON array — use the full label fence,
     e.g. `["self-hosted","general"]`, not a single label), `CLAUDE_REVIEWER_LOGIN`
     (repo variable, this repo's `<slug>[bot]` if the reviewer posts under a
     custom GitHub App), and a `review.focus` line in CLAUDE.md's
     `## sweap config` block for project-specific review priorities.
   - Write the first milestone with `/roadmap` (one file per item under
     `roadmap/`; the `ROADMAP.md` index lists milestones only).

Do not commit — leave the scaffolded files staged-or-unstaged for the human to
review, since CI and verify commands are stack-specific and must be filled in
first.
