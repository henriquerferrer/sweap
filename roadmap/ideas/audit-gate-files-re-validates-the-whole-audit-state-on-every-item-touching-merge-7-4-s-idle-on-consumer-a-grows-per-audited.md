---
title: audit-gate --files re-validates the whole audit state on every item-touching merge (7.4 s idle on consumer A, grows per audited milestone)
created: 2026-09-23T01:49:54.491Z
---

Measured 2026-09-23 on consumer A (264 done items, records for F9 F10 F11 F12 DS.5): pre-merge-gate's audit step takes 7.4 s idle for any PR that touches an item file — the same as a full --check — and 4 ms for a code-only PR. The cost is not history search: merge mode calls validate_record for every record, and each record lints every follow-up it declares (91 roadmap-lint runs, ~55 ms each ≈ 5 s) and runs one path-limited pickaxe (~30 ms) plus one merge-base per done item it covers (~51 each ≈ 2 s). It grows with the follow-ups and done items of every audited milestone, so it will keep creeping. Under a loaded Mac (both CI runners plus an e2e run, load 13) it took 3x that, which is what exhausted the old 10 s per-PR cap on consumer A PR #388 twice (fixed by raising the caps to 50/40 s in 0.31.1 — a knob, not a fix). Why it is structurally redundant: the gate runs --files in the PRIMARY checkout on the base branch, so everything it validates is the base's state, which audit-gate.yml's --check already validated when that state landed on main; the PR's own item changes are not even visible to it. What done looks like: in --files mode, validate only what this merge can change — the records and follow-up files the PR's file list touches, plus the debt question (a complete milestone without any record) which is cheap — and leave whole-state validation to --check on CI, or cache a record's validity keyed by the blob hashes of the record and the files it references. Keep the fail-closed property: an unreadable or unknown base stays a deny. The commit message of sweap #61 and its first comment said the audit step takes 20 ms on PR #388; that measured the empty-file-list fast path and was wrong — corrected in 0.31.2.
