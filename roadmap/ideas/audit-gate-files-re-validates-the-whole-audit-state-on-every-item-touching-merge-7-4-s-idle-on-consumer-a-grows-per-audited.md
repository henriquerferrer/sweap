Superseded on the same day by docs/research/2026-09-23-audit-gate-merge-mode-cost.md. The cache this idea proposed was refuted by demonstration (the validator reads inputs its reads do not name — a done item's `followup_of:` column, replace refs, shallow history, `log.follow`, a lint's `depends_on` probe — so a memo of its "valid" verdicts fails open, and the entry is forgeable). A batched directory-wide pickaxe was built next and died in the hostile review: git history simplification is per pathspec, so a merge TREESAME on the item path but not on the directory makes it attribute a branch-side flip and validate a record that completed after the audit (T75 fences it). What shipped (0.32.0): the per-path pickaxe kept, one rev-list per record instead of a merge-base per item, each disposition reference judged once, the gate anchored at the repo root, hermetic git, the audit-gate check required PRESENT in the rollup, the post-merge backstop naming its timeout. Idle 6.0-7.4 s -> ~4.5 s; at load 16, 32-36 s -> ~24 s (estimated). What remains is a maintainer decision, with numbers in the memo: skip the follow-up lint in merge mode (2 lines, ~2.5 s idle / ~11 s loaded) at the cost of a semantic change no test pins.
